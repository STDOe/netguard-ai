# NetGuard AI — техническое задание v2.0

**Статус:** проект согласованной редакции для утверждения владельцем; не является свидетельством реализации.  
**Дата:** 23 ноября 2026 г.  
**Продукт:** NetGuard AI — Autonomous NetSecOps Harness.  
**Режимы поставки:** самостоятельное приложение (**Standalone**) и интегрируемый специализированный сервис для **AI Workforce OS**.  
**Лицензия (план):** Apache-2.0, окончательно проверить совместимость зависимостей перед публикацией.

> **Назначение документа.** Данный документ — основная спецификация продукта и критерии приёмки. Файл `AGENTS.md` в корне репозитория должен содержать короткие инструкции Codex и ссылку на это ТЗ, а не дублировать весь текст.

## 1. Видение, границы и принципы

### 1.1. Цель

Предоставить специалисту по сетям управляемого AI-помощника, который способен (1) спроектировать новую сеть; (2) обнаружить и объяснить состояние существующей сети; (3) предложить безопасные изменения с проверяемым планом; (4) проверить сетевые политики и представить отчёт; (5) принять события от контролируемых систем обнаружения, включая low-interaction honeypot. В первой версии все изменения ограничены симуляцией, а реальные устройства работают только в будущих, отдельно принимаемых релизах.

### 1.2. Инварианты архитектуры

1. **Два способа использования, одно доменное ядро:** Standalone и Workforce Integration используют одинаковые политики, драйверы, схемы и Change Engine.
2. **NetGuard автономен:** без AI Workforce OS сохраняются веб-интерфейс, API, локальная авторизация, история задач, политики и отчёты. Недоступность Workforce OS не должна останавливать локальные задачи, кроме прямо зависящих от него.
3. **Workforce OS — оркестратор, не сетевой суперпользователь:** подключённая платформа может ставить задачи, читать результаты и запрашивать согласование, но не обходить локальную авторизацию, политики и Change Engine.
4. **LLM предлагает; детерминированный код проверяет и исполняет:** у модели нет произвольного доступа к shell, сетевому CLI, секретам или инфраструктуре.
5. **Fail closed:** неизвестный вендор/версия, недостающие факты, неясное полномочие или ошибка проверки означают отказ от изменения, а не догадку.
6. **Демонстрация не равна доказательству:** Stateful Mock, Containerlab и генерация планов не подтверждают поддержку конкретной аппаратной платформы.
7. **Все внешние данные недоверенные:** содержимое сайта, конфигурации и логи не становятся инструкциями агенту.
8. **Всякое действие прослеживаемо:** кто, когда, откуда, на каком основании, какой план одобрил, какая версия политики применялась и каков итог.

### 1.3. Вне рамок MVP

- Запись конфигурации в реальное оборудование, аварийный самовосстановительный rollback и управляемый периметр в production.
- Автономное блокирование атакующих IP или любое автоматическое изменение Firewall по honeypot-событиям.
- Подтверждённое соответствие PCI DSS / ФСТЭК / ФЗ-152: возможна только карта отдельных проверок и указание непроверенных требований.
- Универсальная поддержка десятков вендоров «из коробки».
- Непроверенная гарантия «один клик — полный откат», SLA/HA и промышленная многопользовательская изоляция.
- Обязательная установка AI Workforce OS для работы NetGuard.

## 2. Пользователи, роли и разрешения

| Роль | Минимальные права |
|---|---|
| Viewer | Просмотр разрешённых устройств, задач, топологии и отчётов (с маскированием секретов) |
| Network Engineer | Discovery, разработка и симуляция планов, запрос согласования |
| Approver | Утверждение конкретных планов в пределах назначенной области; не может сам себе повышать привилегии |
| Administrator | Управление пользователями, интеграциями, секретами, профилями и областями доступа |
| Workforce Service Identity | Только ограниченные API-scopes для постановки/чтения задач и конкретных разрешённых действий; без глобального bypass |

MVP: локальная аутентификация и серверная авторизация для всех API (включая WebSocket), минимум два изолированных тестовых субъекта; запрет анонимного доступа к управлению. Production: дополнительные SSO/MFA, организация/tenant-scoped RBAC/ABAC, сервисные роли, MFA/dual approval для критических изменений. Сервисный аккаунт не равен человеку-утверждающему.

## 3. Доменная модель

Сущности: `Organization` (задел для дальнейшего расширения), `Workspace`, `User`, `ServiceIdentity`, `Network`, `NetworkProfile`, `Site`, `Device`, `Interface`, `Link`, `Subnet`, `Route`, `FirewallRule`, `InventorySnapshot`, `TopologyRevision`, `Task`, `Run`, `StepEvent`, `ChangePlan`, `Approval`, `PolicyEvaluation`, `BackupArtifact`, `AuditFinding`, `Incident`, `Evidence`, `Artifact`, `IntegrationConnection`.

Идентификаторы — UUID/ULID; временные метки — UTC; API использует версии схем, журнал событий упорядочен внутри выполнения; физический `Device` никогда не отождествляется только по пользовательскому имени.

**Статусы задач:** `queued`, `running`, `awaiting_input`, `awaiting_approval`, `succeeded`, `failed`, `cancelled` (возможен `blocked` для отказа политикой). Переходы — контролируемый автомат состояний. Повторная доставка не запускает дублирующее исполнение: `idempotency_key`, уникальная пара `(caller, key)`, блокировка выполнения.

## 4. Сеть и профили

### 4.1. Универсальное ядро

NetGuard не кодирует в Python постоянные подсети или запрет BGP/OSPF. Формальные запреты, разрешённые команды, зоны и требования представлены **версионируемым Policy-as-Code**. Поддержка маршрутизации/HA определяется профилем и capability-декларацией устройства. `L4 Core` описывать точнее: пограничный узел может совмещать L3 маршрутизацию, L4 балансировку, NAT/PAT и Firewall — отдельные технические возможности.

### 4.2. Предустановленный демонстрационный профиль `retail-payment-hub-spoke`

| Зона | Адресное пространство | Назначение |
|---|---|---|
| Infra | `10.10.0.0/16` | DNS, NTP, SIEM/Syslog, NetGuard management |
| Cash / Payment | `10.20.0.0/16` | Критичный кассовый контур, межзонный доступ только по allowlist |
| DMZ / User | `10.30.0.0/16` | Публичные сервисы и изолированные пользовательские сегменты |
| Honeypot | `10.30.99.0/24` | Low-interaction OpenCanary, запрет непредусмотренных исходящих соединений |

Топология Hub-and-Spoke; статические маршруты, BFD только при подтверждённой поддержке обоих концов и после оценки рисков; BGP/OSPF запрещены **только данным профилем по умолчанию**, допускаются отдельным формально утверждённым профилем. Проверки `blackhole`, `rp-filter=strict`, BFD и иные platform-specific правила применяются **условно** — при поддержке устройства, ОС и сетевого дизайна; отсутствие таких механизмов не всегда является нарушением универсальной политики.

Контроль изоляции должен учитывать пути трафика, firewall, NAT, asymmetric routing, а не только совпадение строк конфигурации. Проверка «DMZ не достигает Cash» требует явного тестового метода, разрешённой области и доказательства результата.

## 5. Функциональные сценарии

### 5.1. Greenfield — проектирование новой сети

1. `interview_node`: собрать тип организации, площадки, число пользователей/касс, трафик (Мбит/с и pps), доступность, границы бюджета, допустимых вендоров (включая РФ), HA, сервисы, ограничения compliance, уровень доверия к исходным данным.
2. `requirements_validation_node`: выявить противоречия и недостаток сведений, запросить уточнения до рекомендаций с высокой стоимостью ошибки.
3. `hardware_sourcing_node`: SearXNG/Tavily либо ручное предоставление даташитов; собирать URL, дату обращения, модель/SKU, технический параметр и степень подтверждения. **Нельзя выдумывать цены, наличие, Mpps, BFD, Hardware NAT или L4-функции.** Отсутствие данных маркировать `unverified`; цену не выдавать как актуальную без подтверждения.
4. `architecture_generator_node`: предложить логическую топологию, адресный план, изоляцию, варианты HA, список рисков/компромиссов.
5. `simulation_export_node`: экспорт BOM (MD/CSV/JSON), Mermaid, при наличии поддерживаемого экспортера draw.io, `inventory.yaml`, `topology.clab.yml`. Генерация Containerlab — только для реально поддерживаемых образов и лицензий; иначе объяснить ограничения и предложить mock-топологию.
6. Выдать артефакты с происхождением значений, версиями и предупреждением, что проект нуждается в инженерной валидации до закупки/внедрения.

Запас производительности 35% — **настраиваемое предложение профиля**, не универсальная гарантия. Должны учитываться stateful firewall throughput, NAT sessions, PPS, тип нагрузки и HA, когда данные доступны.

### 5.2. Brownfield — анализ и планирование изменений

1. `discovery_node`: только явный inventory/scope, read-only для реальных устройств в будущей beta; в MVP — State­ful Mock (текущая конфигурация, интерфейсы, маршруты, ACL).
2. `planner_node`: LLM возвращает `ChangeIntent` с типизированными действиями (`add_route`, `remove_route`, `update_acl`, ...), ссылками на исходные факты и желаемым результатом — **не произвольный CLI**.
3. `policy_validation_node`: проверяет разрешение операции, роль, сегменты, запрещённые маршруты, расширение доступа, совместимость с вендором, полноту данных и конфликты.
4. `diff_node`: deterministic vendor adapter генерирует план и diff (для MVP — mock-конфигурацию); показывает область воздействия и ограничения проверки.
5. `human_approval_node`: запрос утверждения **конкретного неизменяемого digest плана**, целевых устройств, оценки риска, срока действия, версии политики и снимка конфигурации.
6. `execution_node`: **MVP — симулированное применение** и проверяемая история; beta — только по специализированной процедуре Change Engine (раздел 8).
7. `post_check_node`: сравнение ожидаемых и фактических инвариантов, формирование результата и свидетельств. Отдельный режим dry-run обязателен.

Перед исполнением план должен повторно проверяться: подтверждение не переносится на изменённый diff или конфигурацию; старый approval недействителен после изменения плана/области/политики или истечения TTL.

### 5.3. Active Defense и аудит

- `compliance_audit_node`: анализ сетевых политик по профилю, детерминированные проверки, разрешённые target-scoped тесты, отчёт по каждой проверке: `pass / fail / unknown / not_applicable`, evidence, затронутые объекты, версия политики, время.
- `Security Score 0–100`: только дополнительный **внутренний индикатор**, формула и веса публичны; `unknown` не считается `pass`; score не равен сертификации.
- `honeypot_incident_node`: принимает строго проверенные события OpenCanary, записывает событие, нормализует IP/время/тип, коррелирует с разрешённым inventory, показывает на карте статус **подозрительного события**, предлагает меру. Не объявляет узел скомпрометированным только по одному срабатыванию.
- Блокировка IP в MVP отсутствует; в beta только через отдельный план, правила защиты, проверку NAT/shared IP и Human Approval.
- `nmap`/активные сканы: строго по утверждённому scope и policy; таймауты, rate limits, логирование. По умолчанию демонстрационные адреса и mock-результаты; никакого сканирования чужих сетей.

## 6. AI-оркестрация и управление LLM

- LangGraph с отдельными ветвями `greenfield`, `brownfield`, `audit/incident`. Состояние хранится надёжно, `thread_id` и версии схем обязательны; восстановление после перезапуска проверяется тестом.
- `LiteLLM` как слой адаптации к поставщикам OpenAI/Anthropic/DeepSeek/Ollama/vLLM; конфиг модели на уровне установки или workspace. Не предполагать, что любая модель умеет одинаковые tool calls / structured output.
- Все действия агента — строго типизированные инструменты Pydantic с явно разрешёнными возможностями. Никакой свободной команды `shell_exec` или `raw_cli` в LLM tools.
- Результат LLM — проект решения; при невозможности верификации возвращать «не подтверждено» либо запрашивать сведения.
- UI передаёт **шаги, состояние, аргументы разрешённых tools, усечённые логи, evidence и результаты**, а не скрытые внутренние рассуждения модели.
- Ограничения количества шагов/токенов/времени, отмена, обработка таймаута и повторной доставки задач. Ретраи применяются только к безопасным идемпотентным операциям.
- Prompt-инъекции: недоверенный текст может дополнительно помечаться тегами для модели, но теги не считаются security boundary. Защита реализуется границей привилегий, allowlist-tools, schema validation, sanitization отображения, изоляцией секретов, политиками egress и тестами на атаки.

## 7. Сетевая драйверная модель и матрица возможностей

`BaseNetworkDriver` предоставляет типизированные read-only методы (`get_facts`, `get_interfaces`, `get_routes`, `get_firewall_rules`, `snapshot`) и декларирует `DriverCapabilities` (OS family/version, read operations, supported intents, rollback mechanism, HA/BFD support, tested firmware). Применение планов разрешено только через Change Engine, а не напрямую из tool call агента.

| Драйвер | MVP | Следующие этапы |
|---|---|---|
| `MockNetworkDriver` | Полноценные read/plan/simulate, сохранение состояния и тестовые ошибки | Фикстуры, моделирование аварийных исходов |
| `CiscoDriver` | Скелет контракта, нет подключения к реальной сети | Read-only IOS-XE по версиям, далее управляемые изменения |
| `MikroTikDriver` | Скелет контракта, нет подключения к реальной сети | Read-only RouterOS v7 по версиям, далее управляемые изменения |
| `GenericCLIDriver` | Не обещать универсальную write-совместимость | Явные vendor adapters с отдельной матрицей и тестовыми стендами |

Предусмотренные библиотеки: Scrapli, TextFSM/ntc-templates, httpx, Netmiko, NAPALM; выбираются по подтверждённой поддержке конкретной ОС. Huawei, Juniper, Arista, Eltex, UserGate, Linux/FRR/nftables — кандидаты на последующие адаптеры, **не обязательные MVP-функции**.

## 8. Change Transaction Engine (реальное применение — после MVP)

Состояния: `draft → validated → awaiting_approval → approved → prechecking → applying → verifying → committed` либо `rejected / expired / blocked / failed / rollback_required / rolled_back / recovery_required`. Запись событий — append-only с проверяемой связью с `task_id`, `device_id`, plan hash и actor.

Для beta каждое изменение:
1. Lock устройства/конфигурации и повторное считывание snapshot; проверка expected revision.
2. Снимок и резервная копия вне устройства; маскирование секретов, шифрование конфиденциальных артефактов, контроль доступа и test restore.
3. Проверка policy, capability и невозможности обхода RBAC; оценка blast radius; проверка зависимости от управляющего канала.
4. Подтверждение конкретного плана уполномоченным человеком, отдельное для Critical по утверждённой политике.
5. Применение только поддерживаемого и протестированного vendor-native режима (candidate/commit-confirmed, safe mode, revert mechanism) с заранее определённым recovery path.
6. Post-check по инвариантам связи, маршрутов, ACL, BFD (если применимо); только после успеха фиксация.
7. При провале — попытка поддерживаемого rollback; если не подтверждён, `recovery_required` и сигнал человеку, без ложного статуса «восстановлено».

Git history — версионный архив конфигураций **не заменяет** vendor rollback. Заявление «откат в один клик» запрещено до независимых end-to-end тестов соответствующих платформ/версий. Таймеры и команды отката нельзя хардкодить универсально.

## 9. Security и эксплуатационные ограничения

**Обязательные механизмы MVP:**
- Политики по умолчанию `deny`, профилирование операций, валидация IP/CIDR, команд и целевых устройств; использование typed intent + deterministic renderer вместо regex-only безопасности.
- Запрет секретов в LLM-подсказках, логах и diff; секреты в отдельном хранилище/переменных окружения для dev, в secret manager для production; ротация, редактирование и маскировка.
- Ролевая проверка на каждом API и WebSocket, CSRF для cookie-сессий, ограничение CORS, XSS-safe rendering HTML/Markdown и обработка журналов как недоверенного ввода.
- Устойчивый аудит попыток запрещённых операций и изменений разрешений; не выдавать токены в UI или экспорты.
- SSRF-защита для `fetch_page_specs` (разрешённые протоколы/домены, deny private/loopback/link-local/metadata IP, проверка DNS redirects), лимиты размера/времени и частоты внешнего поиска.
- Проверка подписи/секрета honeypot webhook, replay protection, rate limit, input schema, разделение происхождения событий и подтверждённых фактов.
- DEMO_MODE=true без боевых сетевых credentials, без доступа к production из демо, отдельные docker networks и минимальные Linux capabilities; сканирование выключено либо ограничено лабораторией.
- Контроль зависимостей, pin/lock версий, аудит лицензий, секрет-сканирование и SAST в CI. CDN UI допустим только для dev/demo; production — локально закреплённые ресурсы с CSP.

**Риски:** потеря управления сетью, lateral movement через агента, prompt injection из CLI/syslog, чрезмерные права service identity, утечка топологии/бэкапов, подмена event webhook, отравление hardware search, ложные security scores. Для каждого должен быть явно описан тест и правило отказа.

## 10. API интеграции с AI Workforce OS

**Режим:** опциональный. Сервис NetGuard предоставляется через версионированный REST API и события; внутри может работать собственный LangGraph. Нельзя связывать базы данных двух продуктов напрямую или импортировать backend AI Workforce OS внутрь NetGuard Core.

### 10.1. Первичный контракт

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/health` | Liveness/readiness (без раскрытия секретов) |
| `GET /api/v1/capabilities` | Версии API, сценарии, поддерживаемые операции и режим (mock/read-only/write) |
| `POST /api/v1/tasks` | Создать задачу Greenfield/Brownfield/Audit в заданной области |
| `GET /api/v1/tasks/{task_id}` | Текущее состояние, прогресс, ошибки и ссылки на артефакты |
| `POST /api/v1/tasks/{task_id}/cancel` | Безопасная отмена (если поддерживается текущим шагом) |
| `GET /api/v1/tasks/{task_id}/events` | Поллинг событий с курсором; WebSocket/SSE опционально |
| `GET /api/v1/artifacts/{artifact_id}` | Выдача авторизованного артефакта |
| `GET /api/v1/approvals/{approval_id}` | Точный план, digest, срок, область, риск |
| `POST /api/v1/approvals/{approval_id}/decision` | Подтверждение/отказ только полномочным субъектом |
| `POST /api/v1/webhooks/honeypot` | Приём заверенного события OpenCanary |

### 10.2. Сквозные требования

- OpenAPI 3.x и машинно-читаемая JSON Schema; `schema_version`, `request_id`, `correlation_id`, `task_id`, `idempotency_key`, `actor`, `workspace_id`, `policy_version` и ссылки на evidence в соответствующих сообщениях.
- Для сервисного доступа: scoped tokens с ограниченным сроком действия, TLS в production, безопасное хранение и ротация, журналирование результата авторизации. Для MVP допускается один защищённый service identity, не административный master key.
- События — `task.created`, `task.started`, `task.awaiting_input`, `task.awaiting_approval`, `task.succeeded`, `task.failed`, `audit.finding`, `incident.detected`. Доставка `at-least-once`, дедупликация получателем, порядок событий определён в рамках одного task.
- Workforce OS может показать страницу подтверждения, но NetGuard **проверяет** личность approver, права, актуальный hash/TTL и требуемую независимость при принятии решения.
- Никакого доступа к raw device CLI / произвольным командам / raw secrets через Workforce API.
- Состояние интеграции `disabled` не должно блокировать Standalone.

### 10.3. Пример типизированного запроса (иллюстрация API)

```json
{
  "schema_version": "1.0",
  "kind": "network.audit",
  "workspace_id": "demo-workspace",
  "scope": {"network_id": "demo-retail-network", "mode": "mock"},
  "parameters": {"profile": "retail-payment-hub-spoke"},
  "idempotency_key": "sample-audit-0001"
}
```

Идентификаторы в примере демонстрационные. `workspace_id` и `network_id` в реальной реализации должны проходить проверку полномочий. API-ответ не должен обещать `succeeded` до завершения выполнения.

## 11. Хранилище и управление артефактами

MVP: SQLite с persistent volume для пользователей, задач, событий, approve records, snapshots и результатов; LangGraph checkpoint — устойчивое хранилище с проверенной совместимостью. Отдельные данные больших артефактов — файловое хранилище с ACL и метаданными (hash, provenance, retention). PostgreSQL — при многопользовательской/производственной нагрузке или требовании HA, миграции заранее через Alembic.

GitPython для истории **санитизированных** конфигураций/артефактов; не записывать секреты в Git и не предполагать, что удаление из текущей версии удаляет их из истории. План резервного копирования БД + артефактов + ключей и **периодическая проверка восстановления** до beta. Логи должны быть минимизированы и иметь retention policy.

## 12. Web UI

MVP: FastAPI + Jinja2 + HTMX + TailwindCSS + Cytoscape.js, отдельные шаблоны/JS-модули (`base`, `dashboard`, `topology`, `chat`, `approval`, `bom`, `audit`), а не гигантский единственный `index.html`.

**Экраны:** обзор workspace и режима, сетевой граф (легенда/состояние источника), чат/шаги агента, инвентаризация, Greenfield wizard, BOM, конфигурационный diff, Approval inbox, Security Findings, настройки/интеграции, история задач.

**Требования UX:** dark mode по умолчанию, адаптивность, 320–1440+ px, доступность клавиатуры, индикаторы loading/error/offline, очевидные различия `mock / read-only / real` и `verified / unverified`; нельзя выдавать симулированное состояние за реальное. Стриминг — структурированные шаги, не внутренний CoT. Дифф показывает device, plan digest, риск, правки и пред/пост-проверки.

Production: локально обслуживаемые статические ресурсы и Content-Security-Policy. Не обещать визуальное равенство React-приложению как инженерный факт; проверять интерфейс по сценариям.

## 14. Этапы реализации и критерии приёмки

**Принцип:** вместо обещания «всё за 5 промптов» — пять этапов, каждый можно разделить на небольшие Codex-задачи и принять независимо. Нельзя переносить красные тесты в следующий этап без явного документированного решения.

### Этап 0 — подготовка проекта и контрактов

- Репозиторий, `AGENTS.md`, Master-ТЗ, architecture ADR, угрозы/ограничения, базовые схемы API/домена, CI, линтер, formatter, тестовый каркас.
- **Приёмка:** `pytest`, статический анализ, проверка imports и startup успешны; документация описывает mock-only границу; тест выдачи/отказа авторизации для API существует.

### Этап 1 — Core + Mock Network + Policy

- Модели устройств, subnet/routes/ACL, фиксированный mock-профиль, сохранение состояния и snapshots, policy evaluator, role checks.
- **Приёмка:** тесты allow/deny, сегментация Cash/DMZ, неизвестная модель/политика → fail-closed, ошибка состояния и перезапуск не создают тихих изменений.

### Этап 2 — Greenfield + Brownfield Planner + Agent

- Interview, sourcing с evidence, генерация topologies/BOM/экспорта, typed intents, diff, approve/reject, LangGraph durable checkpoints.
- **Приёмка:** два воспроизводимых сценария, артефакты проверяются схемами; неподтверждённая цена не появляется как факт; approve недействителен после изменения hash; restart/resume корректен.

### Этап 3 — UI + Audit + Honeypot Demo

- Дашборд, Cytoscape, шаги агента, diff modal, findings, Security Score с формулой; OpenCanary webhook demo без блокировок.
- **Приёмка:** сквозной тест запроса и отображения карты/отчёта; XSS/CSRF и webhook replay negative tests; на UI заметна пометка DEMO.

### Этап 4 — Workforce API + релиз v0.1

- Auth-scoped REST, capabilities, tasks, artifacts, approvals, events, idempotency; compose quickstart, безопасные dev defaults, README/архитектурные диаграммы.
- **Приёмка:** контрактные тесты Standalone и Integration; Workforce API не допускает bypass; повторная отправка task не приводит к дублированию; сборка и запуск с чистой машины по инструкции проверены.

### После MVP: beta и production (отдельные gate)

- **Beta 1:** реальное оборудование **read-only**, отдельные тестовые устройства Cisco/MikroTik, матрица firmware, ограниченное сканирование.
- **Beta 2:** Change Engine с per-vendor apply/rollback, тестами потери связи, race condition, ручного восстановления и ограничением blast radius; только лабораторный стенд до отдельного разрешения на production.
- **Production:** threat review, проникновенные тесты, проверка резервных копий и восстановления, TLS, MFA/SSO при необходимости, observability, operational runbooks, policy governance, нагрузочное/отказоустойчивое тестирование, подтверждённая поддержка устройств/версий.

## 15. Обязательные тесты

1. **Security policy:** обходы CIDR, IPv6/IPv4, default route, wildcard/netmask, NAT, cross-zone, command encoding, неоднозначный vendor syntax, deny-by-default.
2. **Prompt injection:** вредоносные баннеры/логи/поля Inventory, отравленные веб-страницы и события honeypot не могут вызвать tool write, получить secrets, поменять policy.
3. **Authorization:** viewer → deny apply/approve; service identity не может повышать scope; раздельные workspace; WebSocket не обходит API authorization.
4. **Change approval:** привязка к immutable hash, сроку, версии политики/снимка, отказ при изменении запроса; двойная доставка безопасна.
5. **Durability:** рестарт в `awaiting_approval`, повторное получение events, сохранение snapshots, graceful cancellation.
6. **Sourcing:** URL/provenance, отсутствующий даташит → unknown, защита SSRF и внешних redirect.
7. **Audit:** поддерживаемые/неподдерживаемые проверки, `unknown` не превращается в pass; mock scan не выглядит как реальный.
8. **Integration:** contract tests (OpenAPI), токены и scopes, idempotency, event dedupe, standalone запуск с отключённой интеграцией.
9. **Operational:** compose quickstart, dependency scanning, secret scanning, no-privilege demo, backup/restore для beta.

Нет требования искусственно добивать процент coverage: важнее подтверждённые негативные и end-to-end сценарии. Каждый PR: lint/type/test, актуализация документации затронутых контрактов.

## 16. Критерии готовности v0.1 (Definition of Done)

- [ ] Команда запуска из README на чистой среде разворачивает работающий mock-only NetGuard.
- [ ] Локальный пользователь входит в UI, роль реально ограничивает операции API/WebSocket.
- [ ] Есть визуальная карта нескольких сегментов и понятный признак `DEMO`.
- [ ] Greenfield выдаёт адресный план, топологию и BOM/инвентарь с provenance либо метками неизвестных значений.
- [ ] Brownfield строит типизированный план, diff, approval и симулированный результат без доступа к реальным устройствам.
- [ ] Аудит показывает `pass/fail/unknown/not_applicable`, evidence и прозрачную формулу score.
- [ ] Honeypot webhook принимается с проверкой подлинности, событие появляется в интерфейсе, никаких блокировок не выполняется.
- [ ] Действия в mock оставляют журнал, сохраняются после рестарта, повторная задача не исполняется дважды.
- [ ] Workforce API доступен с ограниченным service identity, Standalone полностью работает без Workforce OS.
- [ ] CI-тесты и статический анализ проходят; нет hardcoded secrets, открытых административных endpoints и ненужного privileged контейнера.
- [ ] Документация явно отличает реализованные возможности от запланированных и указывает ограничения поддержки вендоров.

## 18. Открытые решения перед beta (не блокируют MVP)

- Какие конкретно версии Cisco IOS-XE и MikroTik RouterOS v7 будут доступны для тестов?
- Нужна ли изоляция нескольких организаций в одном deployment или на старте допустим отдельный инстанс на клиента?
- Будет ли Workforce OS владельцем SSO/центральных approvals или только внешним инициатором задач?
- Требуется ли полноценная работа без внешнего Интернета (UI asset self-hosting и офлайн-LLM)?
- Какие версии API и соглашения об идентичности уже приняты в AI Workforce OS? В случае расхождения — адаптер с контрактными тестами, а не изменение ядра NetGuard.
- Какие критерии достаточности vendor rollback и out-of-band recovery будут применяться для первых write-enabled устройств?

## 19. Риски исполнения и условия STOP

Codex должен **остановить реализацию опасной операции и сообщить причину**, если: отсутствует подтверждённая device capability; не определён scope/actor; policy fail/unknown; нет валидного approval; источник конфигурации изменился; отсутствует проверенный rollback для заявленного режима; требуется скан неизвестных сетей; предлагается включить доступ к реальному оборудованию в `DEMO_MODE`; обнаружена утечка секрета; не проходят обязательные негативные тесты.

При этом STOP относится к опасному действию, а не ко всей разработке: разрешено продолжать безопасные read-only, mock и документационные задачи. Не создавать ложных заглушек, которые маскируются под «готово»: для отложенной функции возвращать явный `NOT_SUPPORTED` / `NOT_IMPLEMENTED` с указанным этапом.
